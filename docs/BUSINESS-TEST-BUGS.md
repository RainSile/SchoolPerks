## 已确认缺陷

### TEST-001：既有回归测试未完全隔离搜索派生数据（P2，已修复并验证）

- 类型：测试隔离/清理缺陷，暂未发现对账号、订单、优惠等核心业务数据的修改，不能归类为已确认的线上业务故障。
- 前置：已有演示数据的 campus_perks_db；后台派发、交易定时器、搜索重建调度均关闭；仅运行本次明确选定的业务测试。
- 步骤：保存全部 55 张表的行数/逐行摘要 → 执行 `scripts/test-business-backend.ps1` → 再保存摘要并比较。
- 预期：既有测试数据和投影不改变，测试新增记录回滚或按精确 ID 清理。
- 实际：全部 JUnit 断言通过，但 `campus_consumed_event` 从 245 行变为 299 行（+54）；`campus_search_document` 仍 27 行但内容摘要发生变化。其余 53 张表摘要一致。
- 初步定位：社区阶段的全量搜索重建会枚举既有公开资源；搜索消费者使用独立事务。现有 `SearchFixtureCleanup` 和重建清理按本次帖子/商家等资源清理，未完全覆盖对既有资源产生的投影/消费记录。此定位仍需后续逐事件确认，不能仅凭时间范围删除。
- 证据：`.local/business-tests/database-before.tsv`、`database-after.tsv`、`database-differences.json`、`backend.log`，以及 `CommunityStageFiveMySqlTest.rebuildCreatesProjectionAndIncludesTombstoneKeys`、`SearchFixtureCleanup`。
- 影响：重复执行既有集成套件会积累消费幂等标记、触碰既有搜索派生数据，影响测试隔离可信度；目前没有证据显示核心演示账号/商家/优惠/订单被更改。
- 处理：本轮只登记，不改既有清理/业务实现，不按时间或全表删除。后续安全回归脚本默认隔离这一条全量重建用例，避免再次触碰既有资源；这不是对原缺陷的修复。后续统一修复应使用独立测试库/限定范围的测试索引与重建任务，并在执行前保存精确基线键集合；重新比较完整数据摘要。

其余已确认产品缺陷待后续测试登记；以上结果不代表未覆盖功能没有缺陷。

重建测试使用真实游标/公开源/墓碑查询，只在写投影前将资源键限制为两家专属门店及一篇专属帖子；真实租约、持久化、事件和墓碑处理保持原实现。断言每个重建处理 3 个资源，原清理可按 jobId + 精确资源键删除合成消费标记。运行前若已有他人的重建任务则不接管。已恢复此前隔离的测试，专项两项通过，56 表摘要一致。不按时间范围清理历史数据，不回滚不明来源的旧消费标记。

### BIZ-001：可选管理员判断破坏领域内部守卫（P2，已修复并验证）

- 复现：商家发布权限与优惠并发快照用例直接调用领域守卫，合法内部身份没有端标记；新增管理员能力判断调用强制 portal() 并提前抛错，未执行原店主/经理/收银与暂停状态检查。
- 修复：可选判断缺少身份/端标记时安全返回 false；仅明确 ADMIN + business:manage 且无冲突端标记时扩展权限，原领域校验继续执行。
- 证据：三项权限单元测试、14 项商家及18项优惠领域用例已通过；完整回归待复核。

### BIZ-002：跨端管理员的会话被目标端校验拒绝（P1，已修复并验证）

- 复现：真实 ADMIN + business:manage 已获商家 API 权限，但商家看板返回 401；服务将会话真实 ADMIN 身份与目标 MERCHANT 端比较，营销草稿也有同样检查。
- 修复：先按目标端校验已授予的权限，再将持久会话与实际调用者端比较，保留 ADMIN 身份和真实审计 actor。没有跨端授权的账号仍被拒绝。
- 回归：管理员读写商家资料、优惠、两个看板入口、营销草稿列表、本人订单及管理账号接口，同时断言原店主与成员不改变；助手和营销权限回归另行执行。

### TEST-002：新增受限管理员未加入已提交浏览器夹具清理（P2，已修复并验证）

新增权限矩阵使用无跨端授权的管理员作负例，真实浏览器旅程沿用了四账号清理根列表，遗漏第五个新增账号。该账号无角色、无会话且手机号为 test- 前缀，已按核对的唯一 ID 删除并恢复7账号基线。现将该根加入精确清理；其他测试回滚策略不变，不删除任何既有账号。
